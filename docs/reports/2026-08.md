## 1. 현재까지 공부한 내용

### 1.1 DM 타깃의 두 면(facet)

Device Mapper 타깃은 위와 아래에 동시에 면을 가지며, 본 과제의 의미는 이 두 면이
서로 다르다는 데서 나온다는 것을 구현을 통해 체득하였다.

- **위쪽 면**: `io_hints`에서 `BLK_FEAT_ZONED`를 걷어내면 상위(ext4 등)에는
  conventional 블록 디바이스로 광고된다. `/sys/block/dm-X/queue/zoned = none`.
- **아래쪽 면**: host-managed zoned 제약(zone별 write pointer 위치의 쓰기만 허용)은
  타깃 내부에서 임의→순차 변환으로 흡수한다.
- 광고만 바꾸면 임의 쓰기가 그대로 내려가 SEQ_WRITE_REQUIRED 위반으로 거절되고,
  처리만 바꾸면 `mkfs.ext4`부터 실패한다 — 둘을 잇는 LBA→PBA 매핑이 과제의 산출물이다.

### 1.2 LSM-Tree와 ZNS GC의 구조적 동형성

LSM-Tree를 매핑 자료구조로 채택하는 이유를 구현으로 확인하였다.

- LSM-Tree는 **append로 쓰고 컴팩션으로 정리**하고, ZNS는 **append로 쓰고
  zone reset으로 정리**한다 — 두 구조의 모양이 같다.
- 컴팩션이 같은 LBA의 옛 항목을 밀어내는 동작은, 곧 "이 물리 블록은 이제 아무도
  읽지 않는다"는 판정과 같은 일이다. 따라서 **GC의 valid/invalid 판정이 컴팩션의
  부산물로 나온다** — M3에서 GC를 별도 기구로 설계할 필요가 없었던 이유.
- 단, victim 선정의 정확성을 위해 zone별 valid 카운트는 컴팩션 시점이 아니라
  **쓰기 시점**에 갱신해야 한다(덮어쓰기가 죽이는 옛 PBA의 zone을 그 자리에서 감소).
  컴팩션까지 미루면 valid가 과대평가되어 GC가 victim을 잘못 고른다.

### 1.3 커널 6.x 블록 계층 API 변화

6~7월 프로토타입(구커널 VM 기준)이 커널 6.17에서 빌드되지 않아 대체 API를 조사하였다.

| 구 API (5.x) | 커널 6.17 |
|---|---|
| `bio_clone_fast(bio, gfp, bs)` | `bio_alloc_clone(bdev, bio, gfp, bs)` — 5.18에서 제거. 대상 bdev를 인자로 받아 `bio_set_dev()` 불필요 |
| `limits->zoned = BLK_ZONED_NONE` | `limits->features &= ~BLK_FEAT_ZONED` — 6.11 전후로 enum이 feature 비트로 |

### 1.4 bio 제출 경로와 `current->bio_list`

`.map` 콜백은 `current->bio_list`(재귀 방지 메커니즘)가 설정된 구간에서 불린다.
이 상태에서 `submit_bio_noacct()`로 낸 bio는 목록에 쌓일 뿐, `.map`이 리턴해야
실제로 제출된다. 따라서 `.map` 안에서 `submit_bio_wait()`로 자기가 낸 bio의 완료를
기다리면 **자기 교착**이 된다 — 트러블슈팅 4.5에서 실제로 겪었고, dm-zoned 등이
reclaim을 워커 스레드로 빼는 구조적 이유가 이것임을 확인하였다.

### 1.5 zoned 디바이스의 쓰기 순서 보장

zone별 wp 위치의 쓰기만 허용되므로, **PBA 할당 순서와 하위 디바이스 도착 순서가
일치해야 한다.** 발행자(submitter)가 하나면 자연히 지켜지지만, 둘이 되는 순간
(트러블슈팅 4.6) 같은 zone을 공유하면 순서 역전으로 EIO가 난다. 발행자별로
활성 zone을 분리하면 zone 내 순서는 각 발행자가 스스로 지킨다. 근본 해법은
디바이스가 쓰기 위치를 정해주는 `REQ_OP_ZONE_APPEND`로, 실제 NVMe ZNS 명령
경로가 있는 서버 단계의 과제로 남겼다.

## 3. 마일스톤 진행 과정

### 진행 요약

| 마일스톤 | 성공 기준 | 상태 |
|---|---|:---:|
| M0 — pass-through scaffold | `blkzone report` 정상 | 완료 (제공) |
| M1 — 임의→순차 변환 | fio 4K randwrite 100 MB, 거절 0건 | **완료 + 보강** |
| M2 — ext4 라운드트립 | mkfs → dd → umount → remount → md5 일치 | **완료** |
| M3 — GC + zone reset | 80% 채우고 1.2배 overwrite, ENOSPC 없이 완주 | **완료** |
| M4 — 성능 평가 | (서버 단계에서 별도 공지) | 보류 — 서버 필요 |

각 단계는 관찰 가능한 검증을 통과한 뒤에만 커밋하였다 (총 5커밋, 검사 29건).

### 3.1 커널 6.17 포팅

7월까지의 M1 프로토타입이 커널 6.17에서 빌드 불가(1.3절의 API 2건). 포팅 후
기존 성공 기준(delta 0)을 재현하고, 이전에 검증된 적 없던 **위쪽 면 광고**도
확인하였다 — dm 큐가 `zoned=none / nr_zones=0`으로 광고되고 하위 nullb0는
`host-managed`를 유지한다.

### 3.2 M1 정확성 보강 — 성공 기준의 맹점

M1의 성공 기준(fio randwrite의 `blk_update_request` 증가분)은 **읽기를 한 번도
수행하지 않으므로, 쓴 데이터가 제대로 읽히는지는 검증 범위 밖**이라는 점을
확인하였다. 실제로 읽기 경로에 결함이 있었다(4.1절). 검증 수단을 다음과 같이
층층이 보강하였다:

```
delta 0  →  fio --verify=crc32c 왕복  →  차등 읽기 검사  →  (M2) ext4 md5
```

**차등 읽기 검사**: 임의 순서로 흩어 쓴 영역을 1 MiB 큰 읽기와 4 KiB 작은 읽기로
각각 받아 비교한다. 4 KiB 읽기는 블록 하나만 건드리므로 항상 옳다 — 무엇을 썼는지
알 필요가 없는 검사로, 멀티블록 읽기 경로의 결함을 결정적으로 검출한다.

### 3.3 M2 — ext4 라운드트립

mkfs.ext4 → mount → 큰 파일 50 MiB + 작은 파일 100개 → md5 → umount →
`e2fsck -fn` 정상 → remount → **md5 일치**. umount/remount를 끼우는 이유는
페이지 캐시 우회 — 없으면 읽기가 DM 계층에 도달하지도 않은 채 "정상"으로 보인다.

공간 소모 관찰: mkfs만으로 97 MiB(4.7%), 데이터 50 MiB 기록 후 147 MiB.
GC가 없는 시점이라 이 소모는 되돌아오지 않았다 — M3의 필요성을 수치로 보여준다.

### 3.4 매핑을 LSM-Tree로 교체

기존 평면 배열(`kvcalloc`)을 rbtree MemTable → 불변 정렬 run → 컴팩션 구조로
교체하였다. 교체 이유는 두 가지다:

1. **규모** — 평면 배열은 디바이스 전체 블록 수만큼 미리 잡는다. 2 GiB면 4 MiB로
   되지만 32 GiB(서버 FEMU)면 64 MiB, 4 TB 실장비면 8 GiB다.
2. **GC** — 평면 배열은 덮어쓸 때 옛 PBA가 흔적 없이 사라져 "무엇이 죽었는지"를
   모른다. LSM은 그 정보가 컴팩션에서 공짜로 나온다(1.2절).

정확성 회귀(3.2절의 검사 전부)를 LSM 구조에서 재통과시킨 뒤, 공간 회계를 측정하였다:

```
같은 64 MiB 를 4회 덮어쓰기
  소모한 물리 공간   256 MiB
  살아있는 데이터     64 MiB
  쓰레기             192 MiB   ← 디바이스의 75%가 죽은 데이터
  집계된 죽은 매핑   176 MiB   (차이 16 MiB = 아직 flush 전인 MemTable 분량과 정확히 일치)
```

### 3.5 M3 — GC + zone reset 사이클

단일 append log를 zone 순환(FREE→ACTIVE→FULL→GC→FREE)으로 바꾸었다.

- **victim 선정**: FULL 중 valid 최소(greedy). valid==0이면 이주 없이 즉시 reset.
- **이주**: 인덱스 스냅샷에서 후보 수집 → 블록별 복사 → 락 안에서 "매핑이 아직
  그 PBA인가" 재확인 후 갱신(compare-and-swap). FULL zone을 가리키는 매핑은 늘지
  않고 줄기만 하므로 낡은 스냅샷도 안전하다. 경합에서 지면 복사본만 버려진다.
- **교착 방지**: free zone 1개를 GC 전용으로 예약 — 사용자 쓰기는 그보다 많이
  남았을 때만 새 zone을 열 수 있으므로, GC는 이주에 쓸 공간이 항상 있다.
- **테스트 결정성**: `dmsetup message X 0 gc <zone>`으로 victim을 지정할 수 있게
  하여, "GC가 언젠가 그 zone을 고르겠지"에 기대지 않는 검증을 만들었다.

**검증 결과**:

| 검사 | 결과 |
|---|---|
| 결정적 이주: zone0을 정확히 valid 8192로 만들고 `gc 0` 강제 | 정확히 8192블록 이주, used 96→64 MiB, zone0 FREE |
| 이주 데이터 보존: fio `--verify_only` (crc32c 패턴 재검증) | **비트 단위 일치** |
| valid==0 zone: 이주 없이 회수되는가 | 이주 0블록, reset만으로 회수 |
| **M3 공식 기준**: 1600 MiB 채우고 같은 영역에 1920 MiB randwrite | **ENOSPC 없이 완주** — 총 쓰기 3.5 GiB > 디바이스 2 GiB로, GC 없이는 물리적으로 불가능한 워크로드. GC 53회, 이주 412,816블록 |
| 사후 매핑 일관성 (차등 읽기) | 일치 |

### 4.1 멀티블록 읽기 오매핑 — M2 블로커

기존 읽기 경로는 첫 4 KiB 블록의 PBA만 조회하고 bio 전체(최대 128 KiB)를 그
위치로 remap했다. 임의 쓰기로 만들어진 매핑에서는 인접 논리 블록이 물리적으로
인접하다는 보장이 없으므로, 두 번째 블록부터는 다른 LBA의 데이터가 돌아온다.
M1 기준은 읽기를 하지 않아 이 결함이 드러나지 않았다.

수정: PBA가 연속인 구간만큼만 처리하고 나머지는 `dm_accept_partial_bio()`로
DM에 돌려줘 `.map`이 다시 불리게 했다.

**수정의 유효성 증명**: 수정 후 검사 통과만으로는 "검사가 애초에 이 결함을
잡는가"를 알 수 없으므로, 수정 전 코드를 따로 빌드해 같은 검사(동일 randseed)를
돌렸다. 수정 전은 **4098바이트에서 불일치**(= 4096+2, 첫 블록만 맞고 두 번째부터
틀림 — 진단과 정확히 같은 지문), 수정 후는 일치. 검사에 검출력이 있고 수정이
그것을 없앴음을 함께 보였다.

### 4.2 discard를 하위로 통과 — 데이터 파괴 경로

`num_discard_bios = 1`로 광고하고 DISCARD를 하위로 그대로 넘기고 있었다.
상위가 보낸 LBA 범위를 물리 범위인 양 적용하는 것으로, 그 자리에는 다른 LBA의
살아있는 데이터가 append되어 있다. `mkfs.ext4`가 discard를 발행하므로 M2가 이를
처음 밟는 자리였다. 광고를 끄고 미지원 op는 거부하도록 수정. 올바른 구현(매핑
무효화)은 GC 확장 과제로 남겼다.

### 4.3 zone reset·용량 경계 부재

`wp_offset`이 경계 검사 없이 단조 증가만 하여 누적 쓰기가 디바이스를 넘으면
조용히 밖으로 나갔고, 타깃 재생성 시 모듈의 wp(0)와 하위의 실제 wp가 어긋났다.
ctr에서 전체 zone reset(매핑이 in-memory라 하위 잔존 데이터는 어차피 도달 불가),
용량 초과 시 `BLK_STS_NOSPC` 반환으로 수정. M3에서 경계 처리는 GC 재시도로 대체.

### 4.4 인덱스를 오염시킬 뻔한 두 가지 (신규 코드 리뷰에서)

- 인덱스 갱신 **후** clone 할당이 실패하면, 쓰이지 않은 PBA를 가리키는 매핑이
  남는다 → 실패 가능한 일을 전부 잠금 구간 앞으로.
- 다중 블록 쓰기 도중 노드 풀이 모자라면 인덱스가 반만 갱신된다 → 자리를 통째로
  선확인 + `dm_set_target_max_io_len`으로 bio 상한 설정.

### 4.5 `.map` 안의 `submit_bio_wait()` 자기 교착 — 재부팅까지 간 사고

M3 GC의 이주 I/O를 쓰기 경로(.map)에서 직접 동기 수행했더니, M3 부하 테스트에서
fio가 D state로 얼어붙어 kill도 불가, **재부팅으로만 복구**되었다.

원인은 1.4절의 `current->bio_list`: `.map`이 리턴해야 제출되는 bio의 완료를
`.map` 안에서 기다린 자기 교착이다. GC를 전용 workqueue(`WQ_MEM_RECLAIM`)로
옮기고, 쓰기 경로는 `queue_work` + `flush_work`로 워커의 완료만 기다리게 수정.
워커의 I/O는 자기 컨텍스트에서 즉시 제출되므로 안전하다.

`dmsetup message`로 강제한 GC(T1·T2)는 ioctl 컨텍스트(bio_list 없음)라 정상
동작했기 때문에, 쓰기 경로에서 GC가 처음 트리거되는 부하 테스트에서야 드러났다.

### 4.6 두 발행자의 쓰기 순서 역전 — 4.5 수정이 만든 회귀

워커 도입으로 쓰기 발행자가 둘(사용자 + GC 워커)이 되자, 같은 활성 zone을
공유하던 두 발행자의 **PBA 할당 순서와 하위 도착 순서가 어긋나기 시작**했다 —
사용자 bio는 bio_list에서 지연 제출되고 워커는 즉시 제출하므로. 하위 nullb0가
SEQ 위반으로 거부(EIO 다발, 이주 1블록에서 GC 중단).

활성 zone을 사용자용/GC용으로 분리해 해결 — zone 내 순서는 각 발행자(각 1개)가
스스로 지킨다. 사용자 발행자가 여럿인 경우(다중 스레드 direct I/O)는 로컬 검증
범위에서 재현되지 않는 알려진 한계로 코드에 명시했고, 근본 해법인
`REQ_OP_ZONE_APPEND` 전환은 서버 단계 과제로 남겼다.

두 문제(4.5→4.6)는 인과가 이어진다: 교착 수정이 발행자를 하나 늘렸고, 그것이
순서 가정을 깼다. 커밋 메시지에 연쇄를 그대로 기록해 두었다.

### 4.7 테스트 하네스: 스테일 모듈로 시험

`insmod` 실패를 무시하고 진행하면 이미 올라가 있던 **예전 모듈로 시험해 놓고 새
코드를 검증했다고 착각**하게 된다 — 실제로 한 번 발생했다. 모듈 적재 helper가
`/sys/module/*/srcversion`을 빌드된 .ko와 대조하고, 다른 빌드를 내리지 못하면
시험을 중단하도록 만들었다.

### 4.8 6월 질문사항 후속 — teardown 순서 (해소)

"실험 반복에 vagrant halt/up이 필요했다"는 6월 질문은 조교 답변대로 teardown
순서 문제였다. dm 타깃이 하위 nullb0를 참조 중일 때 null_blk부터 내리면 커널이
거부하고 환경이 어중간하게 남는다. 확인 결과 7/1 커밋의 `run_test.sh`가 이미
올바른 순서(`dmsetup remove` → `nullblk-down`)를 따르고 있었다. 이번 달에
mount 단계까지 포함한 3단 teardown(`umount` → `dmsetup remove` → `nullblk-down`)
스크립트로 정리하고, 각 단계에서 무엇을 했고 무엇이 막혔는지 보고하게 했다.
